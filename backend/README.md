# D GOLD Backend (Supabase PostgreSQL + Prisma + Express)

This backend is tailored to the uploaded D GOLD frontend: product catalogue with pouch packs, public COD booking, order tracking by order number + phone, admin order status updates, stock logs, business settings and admin audit logs. There is deliberately no online payment module.

## 1. Supabase setup
1. Create a Supabase project.
2. Open **Project Settings → Database → Connection string**.
3. Put the Session Pooler connection string in `DATABASE_URL` (often works from IPv4-only hosts). Put the direct connection string in `DIRECT_URL` for migrations when direct connectivity is available. Both must include `sslmode=require`.
4. If your host cannot reach Supabase direct database IPv6, use the Supabase Session Pooler URL for `DIRECT_URL` too, or use Supabase SQL editor for migrations. Do not use the transaction pooler for Prisma migrations.

## 2. Install and configure
```bash
cd backend
npm install
cp .env.example .env
```
Edit `.env`: set Supabase URLs, two different random JWT secrets (32+ characters), frontend URL, and a strong initial admin email/password (12+ characters).

## 3. Create schema and initial data
```bash
npx prisma generate
npx prisma migrate dev --name init
npm run db:seed
npm run dev
```
For production after migration files are committed:
```bash
npm run db:deploy
npm run db:seed
npm start
```
Seed is safe to re-run: it creates the admin only if missing, settings if missing and a sample product only when no products exist. It does not overwrite an existing admin password.

## 4. API summary
- `GET /api/v1/health`
- `POST /api/v1/auth/login` `{ "email", "password" }`
- `POST /api/v1/auth/refresh` (refresh cookie)
- `POST /api/v1/auth/logout`
- `GET /api/v1/auth/me`
- `PATCH /api/v1/auth/change-password` `{ "currentPassword", "newPassword" }`
- `GET /api/v1/products`
- Admin: `POST/PATCH/DELETE /api/v1/products`
- `POST /api/v1/orders` public COD booking; body `{ customer:{name,phone,area,address,pin}, item:{productId,packId,qty}, deliveryDate,slot,instructions }`
- `GET /api/v1/orders/track/:orderNumber?phone=...`
- Admin: `GET /api/v1/orders`, `PATCH /api/v1/orders/:id/status` `{status,note}`
- Admin: `PATCH /api/v1/orders/:id/cod` `{codCollected:true|false}`
- Admin: `GET /api/v1/inventory`, `GET /api/v1/inventory/movements`, `POST /api/v1/inventory/adjust` `{packId,delta,note}`
- `GET /api/v1/settings/public`; Admin: `GET/PATCH /api/v1/settings`
- Admin: `GET /api/v1/admin/dashboard`, `GET /api/v1/audit`

Admin routes use HttpOnly cookies. Frontend fetch requests must use `credentials: "include"`. For local development, set `COOKIE_SECURE=false`; production must use HTTPS and `COOKIE_SECURE=true`. If frontend and API are on different sites, configure cookie SameSite=None + Secure and add CSRF protection before deployment.

## 5. Important integration notes
- This is the backend foundation; the uploaded frontend's `src/lib/db.ts` still uses IndexedDB. Replace those calls with `fetch` API methods before expecting devices to share data.
- Existing frontend order IDs were client-generated. New order IDs are generated by the server. Use the returned `orderNumber` in the confirmation screen and track modal.
- The backend enforces stock atomically for tracked packs. A cancelled order restores stock. If you later add returns, add a separate inspected-return workflow rather than automatically restocking delivered orders.
- Prices are stored as whole INR rupees to match the current frontend's `price` and `total` fields. If paise precision or tax calculations become necessary, migrate to integer paise consistently.
- Tracking currently requires order number and phone. Rate limiting is enabled; for stronger privacy, switch to a random tracking token delivered in the booking response/link.
- The backend does not implement image upload yet. Store images in Cloudinary or Supabase Storage and save only the resulting URL in `Product.image`.
- Admin setup is server-side only. Do not keep browser-side admin password hashing or a public create-admin endpoint.

## 6. Production checklist
- Use separate Supabase projects for staging and production.
- Never commit `.env` or expose Supabase database credentials in Vite variables.
- Set allowed `FRONTEND_URL` to the exact production origin.
- Set `COOKIE_SECURE=true` behind HTTPS; configure cross-site cookie policy/CSRF if domains differ.
- Configure Supabase backups/PITR appropriate to the client's plan and test a restore.
- Restrict database access and use a least-privilege database role where possible.
- Review the API with Postman and test concurrent bookings, stock exhaustion, cancellation/restock and login rate limits before launch.
